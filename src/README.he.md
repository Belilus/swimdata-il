# תיקיית `src` — מדריך עומק

כאן הקוד ש**מוציא** נתונים מ־PDF, **טוען** אותם, **מוסיף** תחרות שנייה, ו**מגיש** אותם לאפליקציה ולדשבורד. הלוגיקה של "מי הוא אותו מועדון" בתחרות 1 חיה ב־SQL, לא כאן. כאן חיה הגיאומטריה.

סדר הריצה האמיתי הוא `bash build.sh`:

1. `run_pipeline.py` — תחרות 1: חילוץ → סכימה → נחיתה → `03_transform.sql` → אימות
2. `extract_loglig.py` + `load_loglig.py` — תחרות 2
3. `export_web.py` + `swimedge_adapter.py` + `export_sample_queries.py` — ייצוא
4. בניית `web/dashboard.html` מקובץ אחד

| קובץ | תפקיד |
|------|--------|
| `run_pipeline.py` | המנצח של תחרות 1. מריץ הכול עד מסד מאומת |
| `extract_results.py` | PDF תוצאות אנגלי → CSV |
| `extract_startlist.py` | PDF רשימת זינוק עברי → CSV |
| `extract_loglig.py` | PDF תוצאות עברי של אליפות גדולה → CSV |
| `load_loglig.py` | מוסיף את תחרות 2 למסד הקיים |
| `app.py` | אפליקציית מסוף (דרישת הקורס) |
| `export_web.py` | שאילתות → `web/data.js` לדשבורד |
| `export_sample_queries.py` | מריץ את עשר השאילתות לקובץ מקומי |
| `swimedge_adapter.py` | ייצוא חד־כיווני לצורת SwimEdge (בונוס) |

## הרעיון שמאחורי כל המפרסרים: גיאומטריה

`pdftotext` קורא מילים לפי סדר הטקסט. בעברית מימין לשמאל, עם שמות מועדון שנשברים לשורות, הסדר הזה משקר. העמודות מתערבבות.

הגישה כאן: כל מילה מגיעה עם `(x, y)` מ־`pdfplumber`.

1. מחלקים את רוחב העמוד ל**פסי X** קבועים (נמדדו ידנית על העיצוב של האיגוד).
2. מוצאים **עוגן** בכל שורה — כמעט תמיד שנת לידה, כי זה מספר בארבע ספרות במקום יציב.
3. כל מילה אחרת הולכת לעוגן הקרוב ביותר ב־Y, ואז לעמודה לפי X.
4. בעברית: `pdfplumber` מחזיר גליפים בסדר חזותי הפוך. הופכים כל אסימון עברי (`tok[::-1]`) כדי לקבל עברית קריאה. מספרים לא צריך להפוך.

זו הסיבה שהפרויקט לא "קורא PDF" בצורה כללית — הוא קורא **את הדוח הספציפי הזה** לפי מיקום.

## `run_pipeline.py` — תחרות 1 מקצה לקצה

מחפש ב־`samples/` קובץ עם `results_youth` וקובץ עם `startlist`. אם אין — יוצא עם שגיאה.

אחר כך חמש פעימות:

1. **חילוץ.** מפעיל תהליך־בן ל־`extract_results.py` ול־`extract_startlist.py`. התוצאה: `data/interim/results.csv` ו־`startlist.csv`.
2. **סכימה.** מוחק DuckDB ישן, יוצר חדש, קורא `sql/01_schema.sql`, מוריד `GENERATED BY DEFAULT AS IDENTITY`, מריץ כל פקודה.
3. **טעינה.** `read_csv(..., all_varchar=true)` ישר ל־`stg_results` / `stg_startlist`. עדיין הכול טקסט.
4. **טרנספורם.** קורא את `sql/03_transform.sql` ומריץ. כאן נולדות הזהויות.
5. **אימות.** מדפיס ספירות. בודק שלושה מסלולי מפתח זר (`entry→heat`, `entry→swimmer`, `result→entry`). אם אחד מהם לא אפס — `assert` נופל.

פיצול הפקודות נאיבי: מוחקים שורות הערה שמתחילות ב־`--`, ואז חותכים בנקודה־פסיק. לכן אסור שיופיע `;` בתוך מחרוזת ב־SQL האלה.

הערה: בקובץ `load_loglig.py` כתוב שאפשר להריץ `run_pipeline.py --with-loglig`. **הדגל הזה לא קיים.** תחרות 2 נכנסת מ־`build.sh`.

## `extract_results.py` — תוצאות באנגלית

**קלט:** PDF תוצאות צעירים (עמודות באנגלית, לפעמים רהיטים בעברית).
**פלט:** CSV, שורה לכל שחייה.

פסי X (נקודות על העמוד):

| עמודה | מ־X | עד X |
|--------|------|--------|
| דירוג | 0 | 55 |
| מקצה | 55 | 90 |
| מסלול | 90 | 135 |
| שם משפחה | 135 | 200 |
| שם פרטי | 200 | 270 |
| שנת לידה | 270 | 305 |
| מועדון | 305 | 435 |
| תוצאה | 435 | 500 |
| FINA | 500 | 600 |

איך עובר עמוד:

1. מקבץ מילים לשורות לפי `top` (סובלנות 3 נקודות).
2. מחפש כותרת משחה במבנה `400m Freestyle - Girls 11`. אם החתימה השתנתה — זה משחה חדש (אותה כותרת בעמוד המשך לא מעלה מונה).
3. זורק מילות ריהוט (`Rank`, `Powered`, …) וטוקנים עבריים.
4. עוגנים = שנות לידה שיושבות בפס של שנת לידה.
5. כל מילה במרחק אנכי עד 16 נקודות מהעוגן נכנסת לדלי של אותו שחיין.
6. התוצאה: אם נראה כמו `mm:ss.hh` → אלפיות שנייה. אחרת מחפשים `DNS/DQ/DNF/…` וחוק `SW 4.4`. `DQ` הופך ל־`DSQ`.

המרת זמן: דקות, שניות, מאיות. אחר כך כפול 10 → אלפיות. לדוגמה `1:02.35` = 62.35 שניות = 62,350 אלפיות.

## `extract_startlist.py` — רשימת זינוק בעברית

זה המקור **השני**, והוא קריטי. רק הוא מביא:

- קוד מועדון מספרי
- זמן זינוק (או `NT`)
- שמות עבריים

בלי זה אין פתרון זהויות דטרמיניסטי.

העמוד הוא מימין לשמאל. הקוד ממיין מילים לפי `x0` יורד, הופך כל אסימון עברי, ורק אז קורא כותרות.

מילון סגנונות: חופשי / גב / חזה / פרפר / מעורב.
מילון מגדר: בנות / בנים / מעורב.

כותרת משחה מכילה את המילה `משחה`. כותרת מקצה מכילה `מקצה`. שורת נתונים חייבת מספר מסלול בפס המסלול **ו**שנת לידה תקפה. בלי זה זו שורת כותרת עמודות, לא שחיין.

`NT` לא הופך לאפס: `parse_time_ms` מחזיר `None`, ובמסד זה `NULL`.

## `extract_loglig.py` — תוצאות עבריות של אליפות גדולה

אליפות החורף מגיעה כ־PDF עברי אחד רחב, בלי רשימת זינוק נפרדת. לכן אין כאן `club_code` ואין זמן זינוק.

הבדלים חשובים מול שני המפרסרים הקודמים:

- פסי X אחרים (העיצוב של loglig שונה).
- מגדר כולל גם `נשים`/`גברים`, ואז מנורמל ל־`Girls`/`Boys` כדי לעמוד ב־`CHECK` של הסכימה.
- **גיל מחושב:** שנת התחרות פחות שנת לידה. יותר יציב מכותרות קטגוריה שבורות.
- משחי שליחים (יש `X` במרחק) **מדולגים**. צורת השורה שלהם שונה.
- מורידים תווית קטגוריה שדלפה לתחילת שם המועדון (`בנות 15 …`).

דגל `--year 2025` חובה בשביל חישוב הגיל.

## `load_loglig.py` — איך נכנסת תחרות 2

קורא את ה־CSV של loglig ו**מוסיף** למסד שכבר מכיל את תחרות 1. לא מוחק כלום.

מזהים ממשיכים מהמקסימום הקיים (`max(club_id)+1` וכו').

**מועדונים:** חיפוש לפי שם עברי מנורמל. אם קיים — משתמשים בו. אם לא — יוצרים מועדון חדש עם קוד מלאכותי ≥ 900000, וכותבים וריאנט מקור `loglig`. בפועל נוספו 33 מועדונים כאלה.

**שחיינים:** מפתח `(שם משפחה עברי, שם פרטי עברי, שנת לידה)`. אם האדם כבר קיים מתחרות 1 — אותה שורה. אחרת שורה חדשה בלי שם אנגלי.

בזוג התחרויות הזה החפיפה היא **אפס**: 496 + 815 = 1,311. המנגנון מוכן; האוכלוסיות שונות (צעירים דרום 2026 מול חורף 2025 ארצי).

**משחים / מקצים / רישומים:** לפי חתימת `(מרחק, סגנון, מגדר, גיל)` ו־`(משחה, מספר מקצה)`. כפילות על `(heat, lane)` נזרקת — מסלול אחד, אדם אחד.

אין זמן זינוק בתחרות הזו (`seed_time_ms = NULL`). אם אין זמן גמר — הסטטוס `DNS`.

## `app.py` — האפליקציה שהקורס דורש

ממשק מסוף בכוונה דל. ארבעה דברים, כולם SQL מול הסכימה המנורמלת:

1. טבלת מדליות למועדונים
2. חיפוש שחיין לפי חלק משם משפחה (+ השחיות של ההתאמה הראשונה)
3. השחיות הטובות ביותר לפי נקודות FINA
4. דוח איותי מועדונים (האתגר, כשאילתה)

אפשר תפריט אינטראקטיבי או פקודה חד־פעמית:

```bash
python3 src/app.py
python3 src/app.py standings
python3 src/app.py swimmer MAOZ
python3 src/app.py records
python3 src/app.py variants
```

ברירת מחדל: `build/isa.duckdb`. אפשר לשנות ב־`ISA_DB`. אם הקובץ חסר — ההודעה אומרת להריץ את הצינור.

הדגש למרצה: אלה שאילתות מפורמטות, לא `SELECT *`. אותו SQL ירוץ על PostgreSQL אם מחליפים רק את שורת החיבור.

## `export_web.py` — דלק לדשבורד

מריץ שאילתות על DuckDB וכותב `window.SWIM_DATA = {…}` ל־`web/data.js`. בלי שרת: הדשבורד הוא HTML שקורא את הקובץ הזה.

מה נארז:

- `meta` — ספירות
- `competitions` — שתי האליפויות + כמה שחיות/שחיינים/משחים בכל אחת
- `medals` — זהב/כסף/ארד לפי מועדון ולפי תחרות
- `events` — פודיום (`RANK()` עד 3)
- `swimmers` + `swims` — תיקייה דו־לשונית
- `club_variants` — פאנל האתגר
- `records` — 24 השחיות עם הכי הרבה נקודות FINA

`build.sh` אחר כך תופר את `data.js` לתוך `index.html` ויוצר `dashboard.html` אחד.

## `export_sample_queries.py` — מחברת לשאלות בעל־פה

מפצל את `04_queries.sql` לפי כותרות `Q1`…`Q10`, יוצר את התצוגות, מריץ כל `SELECT`, וכותב עד 15 שורות לקובץ `docs/sample-query-output.txt`. הקובץ **לא בגיט** כי יש בו שמות.

צריך חיבור לכתיבה (לא `read_only`) כי `CREATE VIEW` משנה את המסד.

## `swimedge_adapter.py` — בונוס, לא תלות

קורא את מסד הקורס, כותב JSON בצורת מוצר השחייה של המחבר. **לא נוגע** בקוד או במסד של SwimEdge.

 ממפה ערכים ל־enum: `Freestyle→FREESTYLE`, `Girls→FEMALE`, `50→M_50`, `DSQ→DISQUALIFIED`. בריצה האחרונה: אפס אזהרות מיפוי על 340 משחים.

אם המרצה שואלת — זה להראות שהמודל מהקורס מתכנס למערכת אמיתית. הציון לא תלוי בזה.

## איך לזכור את הצינור במשפטים קצרים

1. **שני PDF שונים** לא חולקים שמות, אבל חולקים מסלול באותו מקצה.
2. **קוד המועדון** הוא האמת. השם הוא רעש.
3. **פייתון** קורא נקודות על הנייר. **SQL** מחליט מי אדם ומי מועדון.
4. **תחרות 2** נכנסת בפייתון כי אין לה רשימת זינוק ואין לה קוד איגוד.
5. **האפליקציה** רק שואלת. היא לא מנקה כלום.
